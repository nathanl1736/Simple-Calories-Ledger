## 0. Product identity in one paragraph

Source: `Calories_Tracker_Product_Design_Document.txt` (v0.1, 2026-04-30; it predates Tidelight, Gemini, meal prep and the new type). Stated identity: "A calm, local-first calorie tracking companion for sustainable weekly consistency"; core phrase "Weekly consistency over daily perfection"; not "a flashy AI-first novelty", not "a strict daily punishment/streak app", not "a medical nutrition app". Stated north-star questions: What have I eaten today? How much room do I have left today? Am I still on track this week? What routine meal can I log quickly? Is my data safe? Stated tone rules (section 5): calm, practical, reassuring; no guilt language; "Estimated, adjust if needed" not "Accurate AI result"; treat incomplete days differently from completed days; "Use 'remaining', 'projected', 'average', and 'on track' carefully". The PDD says "Do not add AI, barcode, cloud sync ... unless explicitly requested" and positions AI Quick Log as "BYO assistant/helper parser". Reality in 2.8.2.0: AI is now the most prominent control (a sparkle button beside the tab bar) and has three Gemini-backed flows plus a copy/paste flow. Free/Pro tiers in the PDD are not implemented (no paywall anywhere in code). App name in UI: "Dawni" (`index.html:14`, `<title>Dawni — weekly food journal</title>`); Settings subtitle "Weekly Calorie Tracker" (`App:6066`); legacy names still leak into file names ("Simple Calories Ledger backup" `backup.ts:315`, `calorie-tracker-backup-DATE.json` `backup.ts:293`, `simple-calories-ledger-photo-DATE.png` `App:1994`).
Energy is called "Cal" in the UI (capital C, Australian usage), with a kJ option (`utils.ts:355-357`: `'kJ'` or `'Cal'`).

## 1. Navigation model

### 1.1 Tabs
- `type Tab = 'tracking' | 'journal' | 'library' | 'stats' | 'settings'` (`App:96`). Labels (`App:100-106`): tracking = **Today**, stats = **Week**, journal = **Journal**, library = **Foods**, settings = **Settings**.
- Only four are in the tab bar: `NAV_TABS = TABS.filter(id !== 'settings')` (`App:108`) so the bar order is **Today, Week, Journal, Foods**. Internal ids differ from labels (stats = Week, library = Foods, tracking = Today).
- Active tab persists across launches in `localStorage['calorie-tracker-active-tab']` (`App:937`, written unguarded at `App:1089`). `storedTab` accepts any tab id including `settings`, so the app can cold-start on Settings (`App:110-114`; legacy value `'cards'` maps to Journal). Selected date never persists; it resets to today on every cold start (`App:938`).
- No router, no URLs per screen, no browser-back integration, no swipe between tabs. (`data-swipe-lock` attributes and the `.screen-swipe-zone` class are vestigial: nothing in JS reads them, `App:718-722, 3141, 5152, 5169, 5260-5362`; `.screen-swipe-zone` only sets a min-height, `css:185-187`.)

### 1.2 Tab bar: look and position
- Markup `AppShell` `App:871-932`: `<div class="tabbar-wrap">` containing `<nav class="tabbar" aria-label="Main tabs">` (four buttons) and, beside it, the sparkle `<button class="log-button" aria-label="Log with AI">`. Rendered after `<main class="app">`.
- It floats: `position: fixed; left/right/bottom: 0; z-index: 40; display: flex; justify-content: center; gap: 10px; padding: 0 16px calc(12px + env(safe-area-inset-bottom)); pointer-events: none` (`css:1971`). Only the children take pointer events. A 96px (+ inset) gradient from transparent to `--bg` sits behind it so content fades out under the bar (`css:1972`).
- The pill: `width: min(270px, calc(100% - 72px)); height: 62px; border-radius: 31px; padding: 4px`, 4 equal columns (~65px each at 390px wide), glass fill `--glass` (`rgba(17,39,43,.66)` dark, `rgba(255,255,255,.72)` light) with `backdrop-filter: blur(16px) saturate(160%/190%)` and an inset hairline highlight (`css:1974`, tokens `css:1678-1683, 1711-1716`).
- Each tab: filled 26px glyph above a 10px label (`css:1975`, glyphs `TabGlyph` `App:864-869`). Active tab = tinted capsule `--tab-active` (`rgba(255,255,255,.10)` dark, `rgba(15,42,46,.08)` light) and `--color-accent-text` colour (`css:1976`). Inactive = `--color-text-soft`. `aria-current="page"` on the active one (`App:918`).
- The sparkle button: 62px circle, accent at 86% opacity over blur, white (or ink, per `accentInk`) filled sparkle glyph 28px (`css:1978`, `App:924-928`). It is hidden while the Settings tab is open (`tab !== 'settings'`, `App:924`).
- The whole `tabbar-wrap` slides down and fades out (`translateY(100% + 24px)`, opacity 0, 0.2s) while a text field outside a modal has focus, as a "keyboard is up" heuristic (`App:872-909`, `css:1973`). `aria-hidden={navHidden}` while hidden. Inside modals the bar is covered by the modal layer (z-index 100) instead.
- On the Settings tab the bar stays visible with no tab highlighted.
- `.app` bottom padding is `calc(118px + env(safe-area-inset-bottom))` so the last row clears the bar (`css:183`); Today adds `.today-screen { padding-bottom: 76px }` (`css:1476`).

### 1.3 What the sparkle ("Log with AI") and "+" do
- **There is no global "+" button in 2.8.2.0.** The release notes still say "+ logs food from any tab" (`src/release-notes.json`, 5th note) and the CSS still has an unused `.fab` (`css:1566`), but no component renders it. "+" glyphs that do exist are row-level: Foods list "log" button (`App:5176`), Now-line chips (`App:2730`), meal-prep rows on Today (`App:2649`), batch rows (`App:5155`), search "Log “x” yourself" (`App:3770`).
- **Sparkle on every tab except Settings** calls `logWithAiFromTabBar` (`App:1129-1132`): if not already on Today it switches to Today (which also resets the selected date to today and scroll to top, see 1.5), then opens the `addFood` sheet titled **"Log with AI"** (`App:2045-2073`). On Today it keeps whichever day is selected, so whatever is logged goes to that day. From Week/Journal/Foods it therefore lands you on Today, with the sheet already over it; cancelling leaves you on Today, not the tab you came from.
- The sheet contents (`App:2046-2072`): three rows with a chevron: **Estimate with Gemini** ("Describe it, or photograph the meal or nutrition label"), **Meal prep a batch** ("List what you cooked and split it into serves to log through the week"), **Help me pick from a menu** ("Snap the menu and get a pick that fits today"); a "Using another AI chatbot?" label with two buttons **Copy prompt** and **Paste estimate**; and the footnote `AI_ESTIMATE_DISCLAIMER` = "AI estimates can be wrong. Review before saving." (`aiQuickLog.ts:327`). The sheet title says "Log with AI" but the stated product rule is "Reposition AI as BYO helper"; there is no non-AI row here (manual logging lives on Today).
- **Manual logging entry points on Today**: the full-width "Log manually" row (`App:2621-2628`, "Type in the calories and macros") and the "Search foods" field (`App:2615-2618`). There is no equivalent on Week/Journal/Foods other than the sparkle.

### 1.4 Settings
- Reached only from the **sliders icon button (aria-label "Settings") in the glass toolbar at the top-right of Today** (`App:2550`), which sets `settingsReturnTab = 'tracking'` and opens the Settings tab with scroll reset (`App:1738-1741`). No entry from Week/Journal/Foods. Also reached programmatically from sheets: "Open Gemini settings" (geminiSetup) and "Open Backup" (backupReminder) via `openSettingsSection` (`App:1110-1115`: closes modal, switches tab, then smooth-scrolls to `#geminiSection` / `#backupSection` after the modal scroll lock releases, `afterModalScrollLock` `App:396-407`).
- Leaving Settings: a glass "Done" pill in the Settings header (`App:6004`) → `setTab(settingsReturnTab.current)`. That ref is initialised to `'tracking'` and only ever set to `'tracking'` (`App:966, 1739`), so Done always goes to **Today (and resets Today to the current date)**, even if Settings was reached from a sheet opened on another tab, or restored as the cold-start tab.

### 1.5 Date navigation
- **Today**: no previous/next-day arrows. A 7-day Mon-Sun strip under the title is the day picker (`App:2555-2586`); tapping a day sets `selectedDate`. Swipe the strip sideways to move a whole week (`useWeekSwipe` `App:2324-2409`; keeps the same weekday, jumps to today when landing on the current week, blocked going forward past the current week with 1/4 rubber-band). A calendar-icon button (`App:2546-2549`) overlays a transparent native `<input type="date">` (opens the OS date picker, blurs after choosing). When viewing another day a glass "Today" pill appears (`App:2544`). Title: "Today", or the long weekday if in the current week, else `readable()` (`App:2542`).
- **Week**: previous/next-week chevrons in a glass toolbar (`App:5692-5693`, next disabled at the current week), a glass "This week" pill when not on the current week (`App:5690`), range text under the title (`weekRange`, e.g. "5–11 October", `App:5614-5622`). No swipe. Tapping a day tile opens that day on Today (`openDayInTrack`, `App:1105, 5766`).
- **Journal**: month navigator `MonthNav` (prev/next chevrons + title "This month"/"Return to this month" over "October 2026", `App:751-766`); day view uses `DayNav` (prev/next arrows and a date pill reading "Today"/"Back to today" over the full date, `App:737-749`) plus a "Month" button. "Open this day" / "Log food for this day" jumps to Today on that date (`App:5342-5344`).
- **Foods/Settings**: none.

### 1.6 Scroll position on tab change
- Scrolling is the document (window) scroll, not an inner container; `html, body { overscroll-behavior: none }` (`css:144`).
- `setTab` (`App:1061-1090`) stores `window.scrollY` for the tab being left (only when no modal holds the scroll lock) and restores the target tab's stored offset in a `useLayoutEffect` before paint (`App:1098-1102`), so Week/Journal/Foods/Settings remember their scroll within a session. **Today always opens at top** and on today's date; Settings/Week openings from shortcuts pass `resetScroll`. Re-tapping the active tab smooth-scrolls to top; re-tapping Journal also resets to the current month (`App:1070-1073`); re-tapping Week resets to the current week and also sets `selectedDate` to today (`App:1074-1077`).
- Scroll offsets are not persisted across launches. Changing week on Week jumps to top instantly (`App:5626-5638`).
- A shared "modal scroll lock" (touchmove/wheel listeners, not `body{position:fixed}`, because of an iOS home-screen bug documented at `App:316-324`) stops the page moving under sheets (`App:272-349`).

## 3. Every modal / sheet

### 3.0 Shared behaviour of `Modal` (`App:529-731`)
- One `modal: ModalName` string in `App` state (`App:97, 946`) decides which sheet is open; only one at a time, except local nested modals (see 3.21). Each sheet is permanently mounted with an `open` prop. Opening a different one while another is open overlaps both for ~180-320ms during the outgoing close animation.
- Markup: `.modal-backdrop > (.modal-scrim) + section.modal-panel[role=dialog][aria-modal=true][aria-label=title] > .modal-head(h2 + close button "Close") + .modal-body`. Title is Fraunces 24px. Close button is a 44px round "X" (`aria-label="Close"`).
- **Presentation depends on width**: at <= 480px every Modal (bottom-sheet flag or not) is anchored to the bottom edge, full width, top corners 22-24px, max-height `96dvh - safe-area-top`, with a 38x4 grabber drawn above the title (`css:1346-1427`). Above 480px they are centred cards, 520px wide (`.wide` 720px, `.lightbox` 680px).
- `bottomSheet` flag changes animation only: bottom-sheet = separate scrim element + panel slides up with a 320ms transform transition from `translate3d(0,110%,0)` (class `entered` added one animation frame after mount); non-sheet = panel fades/rises (`modalPanelIn` 210ms: opacity 0→1, translateY 14px→0, scale .985→1), close 140-180ms.
- **Dismissal**: (1) X button; (2) tap on the scrim/backdrop (`onMouseDown` on the backdrop itself, `App:711-714, 719-721`); (3) swipe down: touch drag from the title bar, or from the content when it is scrolled to the top; the panel follows the finger, the scrim fades to min 25%; release closes if velocity > 0.6px/ms and > 40px, or distance > min(140px, 25% of panel height), else eases back in 220ms (`App:574-668`); ignored when the touch starts on an input/textarea/select or `.swipe-confirm`; (4) Escape closes the topmost modal (`App:670-682`). `closeDisabled` (while Gemini is working in the estimate and batch sheets) blocks all four.
- **Focus**: there is no focus trap, no initial focus (except where noted per sheet), no focus restoration on close, and the page behind is not `inert` / `aria-hidden`; keyboard Tab can reach the page behind (`Modal` contains no `.focus()` call). Exceptions: manual Log food focuses the calories field; the search overlay and the long-press menu manage focus themselves.
- Scroll lock while any sheet is open (`acquireModalScrollLock`, `App:325-349`).
- Sticky action bars: `.modal-body > .actions.vertical` and `.form > .actions.full` are `position: sticky; bottom: -16px` with a top border, soft shadow and bottom safe-area padding (`css:911-923`).
- z-index: tab bar 40, status scrim 45, search overlay 60, long-press menu 80, modals 100, toast 150.
- Some sheets' `onClose` is `setModal(null)` (unguarded) and some are guarded `current === 'x' ? null : current`; unguarded ones can close a sheet that opened in their place when their close animation finishes (risk when changing hand-offs).

### 3.1 `entry` - "Log breakfast|lunch|dinner|snack|drink" / "Edit entry" (`EntryModal` `App:4647-4972`, mounted `App:1918-1945`)

### 3.19 `foodSearch` - "Search foods" overlay (`FoodSearch` `App:3470-3787`)

## 4. Every logging path, end to end

Counting convention: start = app open on Today, current day selected (a cold start actually lands on the last-used tab, `App:937`). "Tap" = one discrete touch inside the app. "Swipe" = the slide-to-confirm drag. Typing, waiting and OS pickers are listed separately. Entries always save to `selectedDate` (`App:1189`), i.e. the day shown on Today (when logging from Foods "+" it is the last day Today showed, which may not be today).
Defaults applied silently (`App:173-211`): meal = Breakfast 05:00-11:59, Lunch 12:00-14:59, Dinner 17:00-21:59, otherwise Snack; but for 10 minutes after the last save the meal and day-part of that save are reused (`App:168-175`). Snack/Drink day-part defaults to that last part or the current clock part (morning <12:00, afternoon <17:00, else evening, `tide:250-254`). Portion defaults to 1 serving (100 g in 100g mode).

### a. Manual typed entry
1. Tap **Log manually** (`App:2621`). `openEntry` (`App:1135`) starts a blank draft on the clock's meal, calls `holdKeyboard('decimal')`, opens the `entry` sheet; the calories field gets focus when the sheet stops moving.
2. Type calories (required). Optional taps: Fat / Carbs / Protein fields, Per 100g toggle, Cal/kJ toggle, meal chip, day-part (snack/drink), name, heart, photo, notes.
3. Swipe the slider (>= 82% travel) → saved. Or tap **Save and add another** (keeps meal+part, refocuses calories; the "log a whole meal" loop).
- Decisions: meal (preselected), day-part for snacks, whether to name it (a name makes it a reusable Recent food; blank → "Lunch entry", not reusable), serving vs 100g, favourite heart.
- Review/confirm: the same sheet; the sticky bar shows "After this: **`N Cal` left today**" and the slider label "Swipe to log `N Cal`". No separate confirmation page.
- Error: nothing typed → toast "Cal required". After save: toast "Entry saved"; the sheet closes; the day-line row appears and the hero number/arc update without animation.

### b. Saved food via search
1. Tap **Search foods** (`App:2615`) → overlay; keyboard comes up; Favourites and Recent are listed immediately.
2. Tap a row (or type to filter; database results appear after >= 2 characters). A saved food opens **Log food** prefilled (numbers per serving or per 100 g, amount 1 or 100, meal from clock, sourceFoodId set). A **database** food first opens the "Food estimate" preview → tap **Use this food** (or "Add to My Foods" to save without logging).
3. Swipe to log. Edit the amount first if needed: tap the "Servings eaten" field (it selects its content), type.
- Taps: 2 taps + swipe (3 gestures); database: 3 taps + swipe.
- Same result via Foods tab: tab (1), "+" on the row (2), swipe (3); the sheet title ("Log lunch") and "After this ... left today|yesterday|on Mon" tell you which day it will land on.
- Via the in-sheet picker: Log manually, search in the picker, tap a result, swipe (4+).
- No match: result list shows "No matches for “x”" and a row "Log “x” yourself / Type in the calories" which opens the manual sheet with the name prefilled.
- Saving updates Recent: named entries create or update a saved food, bump `usageCount`/`lastUsedAt` (`favourites.ts:33-64`); database picks are only saved if hearted.

### c. Favourite / recent
- Same as b (Favourites group is above Recent), or Foods → Favourites/Recent → "+".
- **Now line chip** (Today, breakfast/lunch/dinner windows, see 2.1): 1 tap on a chip opens Log food prefilled with what was logged last time for that usual; 1 swipe saves. Not a one-tap log despite the release note wording ("one tap from logging").
- Hearting happens inside the Log food sheet (heart beside the name) and applies on save; Foods rows have their own heart that toggles instantly with a toast.

### d. Repeat an existing entry
1. **Long-press** (450ms) a day-line row (or right-click / Shift+F10).
2. Tap **Log again today** in the floating menu.
- Immediate: `repeatEntry` (`App:1267-1277`) clones the entry to **today** (not the viewed day) with a new id/createdAt, no photo, same meal/part/notes/estimateSource/batchId. Toast "Entry repeated to today"; no Undo; viewing a past day shows no visible change except the toast. Also available inside the edit sheet as a text link "Log again today" (tap row, tap link).
- Does not touch the saved food's usage count.

### e. Copy day
Does not exist. `grep` for "copy day", "copyDay", "yesterday" finds only date formatting. The PDD lists "copy day" under Pro/Reuse (section 8.2) but nothing is built. Closest existing shortcuts: per-entry "Log again today", Now-line usuals, meal-prep serves.

### f. Meal prep serve
- Create a batch (once per cook-up): sparkle (1) → **Meal prep a batch** (2) → tap the recipe textarea (3) and type ingredients with amounts → adjust the **Serves** stepper (optional) → **Estimate batch** (4) → wait for Gemini (sheet not closable) → review sheet: per-serve numbers (editable), whole-batch ingredient breakdown, confidence + assumptions, Refine → **Save `N` serves** (5) or **Save and log one now** (5). Needs a Gemini key unless "Enter the numbers yourself" (type per-serve Cal etc.). Saved batch appears on Today and in Foods → Meal prep.
- Log a serve: **1 tap** on the batch row on Today (`logBatchServe` `App:1524-1564`). No sheet: logs to the clock-suggested meal and part, portion = min(1, serves left) (the last half-serve logs as 0.5), calories = batch total / serves rounded to whole Cal and tenths of a gram. Toast "Logged to dinner · 3 left" (or "last serve") with **Undo** for 5s. To change meal/amount: tap the new row afterwards. Alternatives: Search → "Meal prep · tap to log a serve" row; Foods → Meal prep → "+".
- Errors: "No serves of `X` left" toast. Serves-left is derived from logged entries, so deleting a serve restores it. Serves are excluded from Recent/Favourites/usuals.

### g. Estimate with Gemini by text
1. Sparkle (1) → **Estimate with Gemini** (2). No key → "Set up Gemini" sheet instead (set-up cost below).
2. Tap the textarea (3) and type what was eaten.
3. **Estimate food** (4). Toast "Estimating… You can close this and navigate again once the result is back." (6s) but the sheet's X, scrim and Cancel are all disabled while loading, so the toast text is wrong for this sheet. Button reads "Estimating…". Typical wait 10-30s (the 10-30s figure is only stated for menus).
4. `entry` sheet opens prefilled (see label/confidence rules below). Swipe (5) to log.
- Decisions: how much detail to type; whether to accept the guessed meal (the model may change it) and numbers.
- Review step: the standard Log food sheet with the estimate block: chip "Estimated" (or "From label"), "High|Medium|Low confidence", bullet "What Gemini assumed", mismatch warning, Refine field. Numbers are normal editable inputs; Per serving/Per 100g toggle converts; "Not an estimate" removes the label.
- What is saved: `estimateSource: 'ai'` (or `'label'`), note text "`notes` Assumed: a; b. Confidence: medium." in `entry.notes`. Confidence and assumptions are not stored as fields; they show again only as notes text. Reopening a saved estimate shows the "Estimated" chip but no confidence chip or Refine.
- Errors: red text inside the estimate sheet (messages in section 5); reply unreadable twice → AI estimate helper sheet pre-filled with the raw text + toast; fetch failure surfaces the browser's raw message (e.g. "Failed to fetch") because it isn't mapped (inferred from `geminiEstimate.ts:597`).
- One-time set-up cost if no key: Estimate (2) → "Open Gemini settings" (3) → Settings opens on Gemini with the key field already in edit mode → paste the key → **Save** (4; it auto-runs Test key and shows the chosen model) → **Done** (5, returns to Today) → sparkle → Estimate again. Roughly 6-8 extra taps plus a trip to Google AI Studio.

### h. Estimate with Gemini by photo
1. Sparkle (1) → Estimate with Gemini (2) → **Add photo** (3) → the OS offers camera / library (usually 2-3 further OS taps; multi-select allowed; max 3 photos, "Add another" afterwards).
2. Optional text (e.g. "ate half the tub"). **Estimate food** (4). Photos are compressed one at a time (1800px longer side, JPEG q .82) and sent as inline base64 with the prompt. The button is disabled while "Adding…".
3. Review sheet as above; swipe (5).
- Packaged-food label photo: model sets `source: "label"`; app shows chip "From label" and the hint "Read from the label photo. Check it matches the pack and the amount you ate."; numbers are per 100 g with "Amount eaten (g)", a "Per 100g" toggle active.
- The estimate photos are not stored and not attached to the entry. To keep a journal photo, tap **Add meal photo** in the review sheet and choose a photo again (different compression: 1000px, q .72).

### i. Gemini refine / correction
- Available only on a fresh Gemini estimate (`estimateSession && estimateDetails && !editingId`, `App:1929`). Steps: tap the "Something off? e.g. small bowl, no cheese" field (1), type, tap **Refine** (2) or press Enter. The app re-sends the original description, the same photos, the previous JSON reply and the correction (`aiEstimate.ts:132-165`). Button shows "Refining…". On success all numbers, name, servings, notes and confidence are replaced by the new estimate; **meal, day-part, attached photo and heart choice are kept** (`App:1471`), but any numbers/name/notes the user hand-edited before refining are overwritten. The correction is appended to the remembered description as "(Correction: ...)".
- Errors appear in red below the field: "Gemini replied in a format Dawni couldn’t read. Try again." or the mapped Gemini message. Batch sheet has its own Refine (kept alongside the recipe so "Cook again" starts from the corrected version).
- Not offered for menu picks, chatbot pastes, edited old entries.

### j. Help me pick from a menu
(Full detail of what is sent, the schema and the entry hand-off: section 5.8.)
1. Sparkle (1) → **Help me pick from a menu** (2) → **Add menu photo** (3) + OS picker (up to 4 photos, "Add page").
2. Optionally change the meal chip (the app guesses from the clock and shows the guess time), type a note.
3. **Suggest what to order** (4). Can be closed; a toast tells you when done ("Your menu pick is ready. Tap Help me pick from a menu to see it." / "Your menu pick couldn’t finish. Open Help me pick from a menu to see why." / "Gemini couldn’t read that menu. Open Help me pick from a menu for tips."). Cancel aborts.
4. Result screen → **Log this** (5) (or "Log" on an alternative) → `entry` prefilled (name as on the menu, per-serving numbers, meal from the pick, notes "Energy printed on the menu." or "Estimated from a menu photo." + assumptions + confidence) → swipe (6).
- Labels: `estimateSource` `'menu'` ("From menu") when the energy was printed, else `'ai'` ("Estimated"); confidence chip; assumptions list.
- Budget logic shown to the user: "Aim for about `lo–hi Cal`" from a share of what's left today (Breakfast 25-35%, Lunch 40-50%, Dinner 80-100%, Snack 15-30%, Drink 5-15%, `menuPick.ts:162-185`).
- Errors: "Add at least one photo of the menu." (inline), "Gemini replied in a format Dawni couldn’t read. Try again.", or notice "Gemini couldn’t read a menu in these photos. Try a closer, well-lit photo of the menu text." (the model's own `note` is used when given).

### k. AI quick log (other chatbots)
1. Sparkle (1) → **Copy prompt** (2) → toast "Prompt copied". Leave Dawni; paste into any chatbot; describe the meal; copy the JSON the chatbot returns.
2. Return; sparkle (3) → **Paste estimate** (4) (`pasteAiQuickLogFromClipboard` `App:1397-1416`; on iOS the system "Paste" confirmation likely adds a tap, inferred).
3. On a good parse the `entry` sheet opens prefilled (`prefillAiQuickLog` `App:1369-1395`): `estimateSource 'ai'` (chip "Estimated"; no confidence or assumptions), `unitMode` from the JSON, amount's leading number → servings (or grams), amount text → serving label, notes → notes. Swipe (5).
4. On a bad parse: toast "Couldn’t read that format. You can fix it below." and the "AI estimate helper" sheet opens with the pasted text. Other toasts: "Clipboard paste is not available here.", "Clipboard is empty.", "Could not read from clipboard."
- The prompt (`aiQuickLog.ts:329-389`) spends most of its length on avoiding double-counting (per-unit values × amount) with a WRONG vs RIGHT example. Settings → "AI estimate helper" has the same prompt, Copy prompt and a "?" help sheet.

### l. Rough meal / day target / day rough guess
- **Rough meal** (2 taps): on the day status card tap **Add a rough meal** (1) → tap a size (2). It logs at once and closes (toast "Rough dinner logged: 800 Cal"). Optionally pick the meal chip first. Typed alternative: "Or type a number" + Log. Also from Log food → "Add a rough meal" (3 taps). The card's buttons are hidden on today before 17:00 while under 90% of target (see 2.1).
- **Day target** (2-4 gestures): Target button (1) → drag the slider or type a number + **Set** (2) → close the sheet (3). Persists on each change; Today's hero and "left" update live behind the sheet. Not offered for past days.
- **Day rough guess** (2 taps): **Rough guess for the day** (1) → option "About on target" / "A bit over" / "Big day" (2) → toast "Rough guess saved". Replaces the day's logged total in the week bank. "Use my log instead" reverses (toast "Using your log").
- **Done for today** (1 tap, or 2 if the day looks light): marks the day complete so it counts toward the week immediately (toast "Counted toward your week"; Undo link reverses with toast "Undone").

### Cross-cutting: how estimates are labelled
- `Entry.estimateSource` ∈ `'ai' | 'label' | 'menu' | 'rough' | null` (`types.ts:8, 51`); labels `Estimated | From label | From menu | Rough guess` (`aiEstimate.ts:287-296`). Shown: day-line sub text (`App:2902`), "≈" before calories for rough entries (`App:2907`) and saved estimates in Foods (`App:5175`), Journal chips, search row meta, Log food chip, Foods rows, batch rows.
- Confidence (`High|Medium|Low`) and assumptions are shown only while reviewing a fresh Gemini/menu result and are then flattened into the entry's `notes` string.

## 5. Gemini integration behaviour

Files: `geminiEstimate.ts` (transport, models, errors), `aiEstimate.ts` (meal prompt, schema, parser), `mealPrep.ts` (batch prompt/schema/parser), `menuPick.ts` (menu prompt/schema/parser/budget), `aiQuickLog.ts` (chatbot prompt and tolerant JSON parser). Calls go straight from the browser to `https://generativelanguage.googleapis.com/v1beta` with the user's key in the URL query (`geminiEstimate.ts:23, 516`). There is no backend.

### 5.1 Key entry and validation (Settings → Gemini card, `App:6018-6047`)
- Field is a `type="password"` input, disabled until **Edit** is tapped; placeholder "Tap Edit to add or change your key" / "Paste API key". **Save** trims and stores it in `settings.geminiApiKey` (IndexedDB app state, included in exported backups) with toast "Gemini API key saved" ("Gemini API key cleared" if empty). If the key changed and is non-empty, a check runs immediately (`App:5985-5998`): "paste, Save, done".
- **Test key** (`probeGeminiKey` `geminiEstimate.ts:652-686`): lists the key's models (free), ranks them, then pings each from the top with a 16-token "Reply with the word OK." request until one answers; a free key's Pro rejections are instant and free, a paid key costs one capped call (per the help sheet, "a fraction of a cent"). Result states (`GeminiKeyStatus` `App:5863-5894`, verbatim):
  - testing: "Checking which Gemini models this key can use..."
  - ok: "Ready. Dawni will use **`Gemini 3 Flash`**." with ", the best model this key can use." appended when it's the top model on a paid key; on a free key an extra line "This key is on Google’s free tier. Pro models need a paid plan; if you upgrade, tap Test key and Dawni moves up to the best model."; and a small mono line `gemini-3-flash-preview · 38 models listed for this key`.
  - error: the friendly message in red + disclosure "Details from Google" with the raw API text.
  - no key: "Not set up. Add a key to use Estimate with Gemini and Help me pick from a menu."
  - saved key, not yet tested: "Dawni uses **`model`**[ on Google’s free tier]. Tap Test key to check again." (from the cached profile) or "Key saved. Tap Test key to see which Gemini model Dawni will use."
- Model names for people come from `geminiModelLabel` (`geminiEstimate.ts:327-342`), e.g. `gemini-3.1-flash-lite-preview` → "Gemini 3.1 Flash-Lite (preview)".
- **No-key state elsewhere**: Estimate with Gemini and Help me pick from a menu open the "Set up Gemini" sheet instead (3.13); the batch sheet's primary button reads "Set up Gemini to estimate". The chatbot copy/paste route and manual entry keep working.

### 5.2 Model selection and cascade (`geminiEstimate.ts:1-60, 240-345, 378-460, 619-745`)
- Nothing names a required model. For each request: use the last working model for this key if it answered within 24h (`MODEL_CHOICE_TTL_MS`) and its plan check is under 7 days old (`PLAN_TTL_MS`); otherwise `models.list` (keep `generateContent` models whose id starts with `gemini` and excludes embedding/aqa/tts/audio/imagen/image/veo/live/vision-only/computer-use/robotics) ranked by `familyVersion x 1000 + tier x 10 - stability penalty` (tier: ultra 40, pro 30, flash 20, other 15, lite 10; penalty: preview 8, `-latest` alias 3, dated snapshot 2); `-latest` aliases inherit the newest family number. Fallback ids if listing fails: `gemini-pro-latest, gemini-flash-latest, gemini-2.5-pro, gemini-2.5-flash, gemini-2.0-flash`.
- Walk best-first. A model the plan refuses (429 with `limit: 0`, or text naming free/paid tier) is recorded as `paidOnly`, moved to the back along with everything of equal or higher tier, and does not count as an attempt; a free key therefore reaches Flash in one hop. Caps: 8 counted attempts, 16 total (`MAX_MODEL_ATTEMPTS`, `MAX_TOTAL_ATTEMPTS`). Per model, up to 4 tries, stepping capabilities down when a 400 names them: `responseSchema`, then `responseMimeType: application/json`, then `systemInstruction`.
- Key-level failures (401/403, invalid/expired key, API not enabled, billing broken, region) stop immediately rather than cascading.
- If a reply fails the parser (`accept`), the same model is asked once more with the note "Your previous reply could not be read. Reply again with only the JSON object in the exact shape described, with no other text." (`aiEstimate.ts:125`), once per request.
- Temperature: 0.2 only for explicit gemini-1.x/2.x ids; Gemini 3+ and aliases use the default (`geminiEstimate.ts:499-501`).
- What the user is told about model and tier: only in Settings (status lines above) and the help sheets. The estimate / menu / batch sheets never show the model, tier, or wait-cause.
- Per-key knowledge is cached in IndexedDB key `geminiKeyProfile` (hash fingerprint of the key, last model, resolvedAt, freeTier, paidOnly, planCheckedAt).

### 5.3 What the prompts instruct (serving vs 100 g)
Meal estimate system prompt `GEMINI_ESTIMATE_PROMPT` (`aiEstimate.ts:64-122`), and a structured-output schema `ESTIMATE_SCHEMA` (`aiEstimate.ts:43-62`) with fields `source, name, meal, basis, servingsEaten, servingDescription, servingGrams, gramsEaten, total{calories,protein,carbs,fat}, per100g{...}, assumptions[], confidence, notes`.
- Source: `"label"` if a nutrition panel is readable (read, don't estimate), else `"estimate"`.
- Basis (verbatim intent): `"serving"` "for a dish or meal: anything cooked or put together from several ingredients (including when the user lists the ingredients and amounts they cooked with), restaurant, cafe and takeaway food, sandwiches, bowls and plates, and countable things eaten without a weight (2 eggs, 1 banana, 1 large latte). The app shows one serving's numbers times servings eaten."; `"100g"` "for one single food or packaged product when the grams (or mL) eaten are known: a label reading, or a plain food the user weighed ... The app shows the per-100 g numbers times grams eaten"; "If unsure, use 'serving'."
- Numbers: `total` = everything eaten in this entry, all servings combined; `servingsEaten` = how many identical servings the total covers; `servingGrams` = weight of one serving when known; `gramsEaten` always set for 100g; `per100g` for labels/100g else zeros; for 100g, `total = per100g x gramsEaten / 100`; recheck 4/4/9 consistency.
- Home cooking: count every ingredient incl. oil/butter/sauces; if the recipe made N serves and the user ate one, `total = whole / N`, `servingsEaten = 1`, `servingDescription "1 of 4 serves"`; if serves unknown and the amounts are clearly a batch, assume typical serves and say so in `assumptions`; set `gramsEaten` only for a weighed finished portion.
- Australian specifics: kJ → kcal ÷ 4.184, "Never put a kJ number in a calorie field"; typical Australian portions.
- Request text (`buildEstimateRequest` `aiEstimate.ts:132-165`): `ESTIMATE REQUEST`, `Local time: <weekday, time en-AU>`, `Meal: <meal>`, `About the user: <preferences or 'nothing saved'>`, `Photos attached: N`, `What they ate: ...` (+ `Previous estimate`, `Correction from the user`, instruction to keep unchanged parts when refining).
- Batch prompt (`mealPrep.ts:56-88`): one JSON with `name`, per-ingredient `{name, amount, calories, protein, carbs, fat}` for the whole batch, `total`, `assumptions`, `confidence`; "Do not divide by the number of serves: the app does that"; count only what's listed; weights are as bought (raw) unless the user says cooked. The app recomputes `total` as the sum of ingredients (`parseBatchEstimate` `mealPrep.ts:154-178`).
- Menu prompt (`menuPick.ts:64-114`): recommend only dishes in the photos using the menu's name, aim for the suggested range, follow goal mode (Cutting/Maintaining/Bulking), favour protein when much is still to go, "Calm, practical and kind. Australian English. No guilt or shame language (never 'cheat', 'bad', 'burn it off' or 'failed')", short fields (reason ≈15 words, tip ≈10, summary ≈40), up to 2 alternatives, `menuReadable:false` with a note when unreadable. Request text includes goal mode, targets, eaten so far, remaining, protein to go, everything already logged today (up to 20 items), user note, preferences.

### 5.4 Mapping Gemini fields → Entry fields
Parser `parseGeminiEstimate` (`aiEstimate.ts:214-270`) → `GeminiEstimate` → draft (`prefillGeminiEstimate` `App:1450-1476`) → entry (`formEntry` `App:1182-1211`, `normalizeEntry` `state.ts:36-61`).
- `basis:"100g"` **and** `gramsEaten > 0` → `unitMode:'100g'`, `portion = gramsEaten` (1 dp), base = `per100g` if its calories > 0, else `total / (gramsEaten/100)`. (A 100g reply without grams falls through to serving.)
- Otherwise `unitMode:'serving'`, `portion = servingsEaten` (rounded to 2 dp; missing → 1), base = `total / portion` (so a multi-serving order isn't counted twice), `servingGrams = gramsEaten/portion` if grams given else `servingGrams`.
- `servingDescription` → `servingLabel` (draft/Food only; the Entry type has no serving label; it is shown as the caption under "Servings eaten").
- A reply with no `basis` (older shape): `label` → 100g, else serving. A flat legacy reply (`calories` at top level, no `total`) goes through the chatbot parser instead.
- `meal` → draft meal (falls back to the clock/last-logged meal); `source:'label'` → `estimateSource:'label'`, else `'ai'`; `confidence`, `assumptions` → the review block and flattened into `notes` by `estimateNotes` ("`notes` Assumed: a; b. Confidence: medium."; labels use "Read from the nutrition label.").
- Entry fields written: `unitMode`, `portion` (servings, or grams in 100g mode), `baseCalories/baseProtein/baseCarbs/baseFat` (per serving or per 100 g, from the draft text: Cal to whole numbers (kJ to 1 dp), macros to 0.1 g), `calories/protein/carbs/fat` (derived totals = base × `portion` or `portion/100`, recomputed on every normalise), `estimateSource`, `notes`, `meal`, `part`, `sourceFoodId` (null for AI results), `autoNamed` if the name is blank.
- Rounding consequence: Gemini's `total` is divided by `portion` into an unrounded base, but the sheet shows and saves the base rounded to whole Cal, so the saved total can differ from Gemini's total by up to `portion × 0.5` Cal.

### 5.7 Timeouts, cancellation, storage
- **No request timeout anywhere** (no `AbortSignal.timeout`, no timer). The estimate and batch sheets cannot be closed while a request runs (`closeDisabled`), and their Cancel button is disabled, so a stalled request leaves the sheet stuck until the browser's own network failure. Only Help me pick from a menu has a Cancel (an `AbortController`, `App:4313, 4546`) and can be closed mid-request.
- Offline: no special handling; a failed fetch surfaces the browser's own text.
- **Photos**: estimate and menu photos are held in React state only, sent as base64 inline parts, never written to IndexedDB. Estimate photos stay in memory in `estimateSession` for Refine until another estimate or a reload. Menu photos stay in the (always-mounted) sheet's state until "Start a new menu" or reload. A meal photo attached to an entry is a separate, separately-compressed upload.
- **AI reply**: the raw JSON is not saved. In memory: `estimateSession.reply` (for Refine). Persisted: the entry's numbers + notes text; a Food snapshot (name, basis, numbers, `estimateSource`); for batches `recipe`, `ingredients[]`, `assumptions`, `confidence`; the last menu pick (full result, no photos) in IndexedDB key `menuPickLast` for 3h and same date only; the key profile.
- **What is sent**: the system prompt, the request text, photos, and the "About you, for AI" preferences (≤ 500 chars) with every call; for menus also the day's totals/targets/logged items.
- **30-day pruning** (`favourites.ts:66-83`, run once at app load `App:995-999`): a saved Food is removed from Recent/Search (diary entries untouched) when `estimateSource` is `'ai'` or `'menu'` (not `'label'`, not typed-in), it is not a favourite, `usageCount <= 1`, it hasn't been edited in Foods (`updatedAt - lastUsedAt` within 60s), and `lastUsedAt` is older than `ONE_OFF_ESTIMATE_DAYS = 30`. Surfaced to the user only in the Recent hint: "AI estimates you only log once clear after 30 days, unless you heart them."

The system prompt text is `MENU_PICK_PROMPT` (`menuPick.ts:64-114`), sent as `systemInstruction` when supported.

**Response schema** `MENU_PICK_SCHEMA` (`menuPick.ts:134-144`) with item schema `MENU_ITEM_SCHEMA` (`menuPick.ts:116-131`):
- top level: `menuReadable: BOOLEAN` (the only required field), `pick: item`, `alternatives: item[]`, `summary: STRING` ("At most two short sentences"), `note: STRING` ("One short sentence, or empty").
- item: `name: STRING`, `calories`, `protein`, `carbs`, `fat: NUMBER`, `reason: STRING` ("One sentence, at most about 15 words"), `tip: STRING` ("At most about 10 words, or empty"), `fromMenu: BOOLEAN`, `assumptions: STRING[]` ("Up to 3 short phrases"), `confidence: STRING` ("high", "medium" or "low"); required: `name, calories, protein, carbs, fat, reason`.
- There is **no `meal` or `portion` field**; the meal always comes from the chip the user selected, and every item is one serving.
- Parsing (`parseMenuPick` `menuPick.ts:276-299`, `menuItem` `251-273`): calories rounded to whole numbers, macros to whole grams, `fromMenu === true` forces `confidence:'high'`, assumptions trimmed to 3, up to 2 alternatives deduped by name; `menuReadable:false` returns a note only; a reply without a usable `pick` is "unreadable" and triggers the one-time retry (`App:4329`, `geminiEstimate.ts:708-713`) and then the error "Gemini replied in a format Dawni couldn’t read. Try again." (`App:4334`).

**How a picked item becomes an entry**: `prefillMenuPick(item, meal)` (`App:1428-1447`, wired `App:2042`, called from **Log this** `App:4418` and each alternative's **Log** `App:4435` with `activeSession.meal`). It clears `estimateSession` (so no Refine, `App:1431`) and `flushSync`-sets the entry draft: `blankEntryDraft(meal)` + `name = item.name`, `calories/protein/carbs/fat` from the item, **`estimateSource = item.fromMenu ? 'menu' : 'ai'`**, **`notes = estimateNotes(item.fromMenu ? 'Energy printed on the menu.' : 'Estimated from a menu photo.', item.assumptions, item.confidence)`** (→ e.g. "Estimated from a menu photo. Assumed: large serve of chips. Confidence: medium."), `estimateDetails = {confidence, assumptions}` (drives the confidence chip and assumptions list in the sheet), then `setEntryOpenMode('prefill'); setModal('entry')`. Defaults left as blank draft: unit mode "serving", amount 1, no source food, no photo. The user still has to swipe to log (`saveEntry` `App:1242`); it also creates/updates a Recent food with `estimateSource` 'ai'/'menu' (so it is subject to the 30-day prune, 5.7). Nothing is logged by the menu sheet itself.

**State and persistence**: `MenuPickSession {version:1, date, createdAt, meal, remainingAtRequest, proteinLeftAtRequest, result}` (`menuPick.ts:54-62`) is kept in component state and in IndexedDB `menuPickLast` (`saveLastMenuPick` `menuPick.ts:317-323`); `isMenuPickFresh` requires same date and age ≤ 3h (`menuPick.ts:303-309`); reloaded on mount/date change (`App:4259-4271`). After logging a pick the session remains and re-opens on the same result ("Back to suggestion") with no "logged" marker. Cancel uses an `AbortController` (`App:4313, 4546`); closing the sheet mid-request keeps it running and a toast reports the outcome (`onBackgroundNotice` → `notify(message, 4000)` `App:2043`).

**Reusable vs photo-specific pieces** (for a free-text variant): reusable as-is: `buildMenuPickContext`, `mealBudget`, `MODE_RULE`, the result card UI (pick + alternatives + summary + Log buttons), `prefillMenuPick`, session persistence. Photo-bound: the prompt's "Only recommend dishes that appear in the photos" and `menuReadable` branch, `requestMenuPick`'s mandatory-image guard, the Suggest button's `!photos.length` guard, the setup screen copy/photo grid, the result footer "Estimated from a menu photo. ...", the `fromMenu` flag (meaning "energy printed on the menu"), and the `notes` lead string.

## 6. Data model summary

### 6.1 Entities (`types.ts`)
- **Entry** (`types.ts:31-58`): `id, sourceFoodId|null, date 'YYYY-MM-DD', name, autoNamed?, unitMode 'serving'|'100g', baseCalories/baseProtein/baseCarbs/baseFat` (per serving or per 100 g), `portion` (servings, or grams in 100g mode), `calories/protein/carbs/fat` (the logged totals, always recomputed as base × (portion, or portion/100)), `meal` (Breakfast|Lunch|Dinner|Snack|Drink; default Snack), `part?` (morning|afternoon|evening, only stored for Snack/Drink), `estimateSource?` ('ai'|'label'|'menu'|'rough'), `batchId?`, `notes?`, `photo?` (JPEG data URL), `createdAt`, `updatedAt`. Day ordering = part (derived from meal or `part`) then `createdAt` (`tide:282-287`, `utils.ts:104-106`). Normalisation `state.ts:36-61`.
- **Food** (`types.ts:96-118`): saved/Recent/favourite food: name, basis, brand, servingLabel/Grams, source/sourceId (database origin), category, tags, per-unit numbers, `estimateSource?`, `favourite`, `usageCount`, `lastUsedAt`, `createdAt`, `updatedAt`. "Recent" = any saved Food sorted by `lastUsedAt`; "Favourites" = `favourite: true`. Rules `favourites.ts:33-64`.
- **Settings** (`types.ts:10-27`, defaults `state.ts:8-34`): `calories 1800, protein 150, carbs 90, fat 50` (defaults), `accent '#0E7C76'`, `theme 'light'`, `trackingMode 'Cutting'`, `energyUnit 'kcal'`, backup fields (`lastBackupAt`, `lastBackupMeta`, `lastBackupReminderShownAt`, `backupReminderDays 7`), `geminiApiKey`, `aiPreferences` (<=500 chars), `spreadWeeklyBank false`. A legacy default (2000/150/200/65) is migrated to 1800/150/90/50 on load (`state.ts:101-105`).
- **AppState** (`types.ts:146-160`): `settings, entries[], foods[], completedDates[], dayEstimates{date→kcal above target}, dailyGoals{date→snapshot}, dayCalorieOverrides{date→kcal}, customFoodDatabases[], batches[]`.
- **DailyGoalSnapshot** (`types.ts:29`): `{calories, protein, carbs, fat, trackingMode}` frozen per day.
- **Batch** (`types.ts:74-94`): meal prep: name, recipe text, `servings` (1-30, default 4), `total` (whole batch), `ingredients[]`, `estimateSource`, `assumptions`, `confidence`, `cookedOn`, `finishedAt`. Serves left = servings − Σ(portion of entries with that `batchId`) (`mealPrep.ts:196-207`). Active for 7 days after `cookedOn`; finished batches keep the last 5 (`mealPrep.ts:7-11, 214-240`).
- **Persistence**: whole `AppState` is one object in IndexedDB `calorie-tracker-db` / store `kv` / key `state` (`storage.ts:1-71`), rewritten on every change after `normalizeStateShape` (`App:980-985`); extra IndexedDB keys: `geminiKeyProfile`, `foodEstimateDatabaseCache`, `menuPickLast`. localStorage keys: `calorie-tracker-active-tab`, `calorie-tracker-library-sub`, `dawni-theme`, `dawni-accent`, `dawni-macro-view`, `calorie-tracker-update-prompted-version`. Built-in food database: `public/commonfooddb/baselinedb.json` (2,618 records, ~1.5 MB, fetched on first search then cached in IndexedDB; `foodDatabase.ts:166-211`).

### 6.2 Goals per day, day targets, rough guesses
- **Goal snapshots** `dailyGoals` (`utils.ts:170-176`): `goalForDate(date)` returns the stored snapshot if the date is in the past or the day is completed, else the *current Settings*. Snapshots are created when a day is completed (`setDayComplete` `utils.ts:113-125`), when a rough guess is set (`utils.ts:133-145`), on load for any past date that has records (`lockPastGoals` `utils.ts:343-349`, called from `normalizeStateShape` `state.ts:138`) and just before saving new goals (`App:1813-1816`), so changing your target never rewrites history.
- **Day calorie override** (`dayCalorieOverrides`): optional kcal target for today or a future day, set from the Target sheet. Applied only through `resolveDayCalorieTarget` (`utils.ts:301-316`): `suggested = max(1, base goal + spread adjustment)`; override is clamped to the slider bounds (`utils.ts:284-288`) and ignored when within max(25, 1.5%) of `suggested`; past days ignore overrides. Macros keep their usual targets.
- **Spread** (`spreadWeeklyBank`; `utils.ts:274-282`): when on and the date is one of that week's remaining days and `banked != 0`: `adjustment = max(banked / remainingDays.length, -goal × 0.2)`; so a saving is shared equally and an overrun never takes a day below 80% of its target (the rest "stays in that week's result"). This changes only the displayed target on Today (hero, "Target N · with bank", Log food "after this" line, menu-pick context); it does not alter the bank maths.
- **completedDates**: days confirmed by "Done for today" / "That's everything"; cannot be set for future days. **dayEstimates**: kcal above the day's target (0 = about on target, +500, +1000 offered; stored range clamps to -5000..10000, `state.ts:127`).

### 6.3 Week bank rules (`utils.ts:178-282`, tests `tests/weekBank.test.mjs`)
- Weeks run Monday-Sunday (`weekStartMonday` `utils.ts:55-60`).
- `LIGHT_DAY_SHARE = 0.6`, `SPREAD_FLOOR_SHARE = 0.8` (also mirrored as `PLAN_FLOOR_SHARE` `tide:187`).
- Per-day status `bankDay` (`utils.ts:206-222`), first match wins: **upcoming** (after today) → **estimated** (a rough guess exists; counts as `goal + guess`) → logged <= 0 kcal: **today** (in progress) or **untracked** (past; counts as on target, i.e. no effect) → in `completedDates`: **counted** → is today: **today** (in progress) → past, unconfirmed and logged < 60% of that day's goal: **light** (held out, "counts as on target" until checked) → else **counted**. Only *counted* and *estimated* days have an `intake`; `delta = goal − intake` (positive = under target).
- "Completed vs incomplete": today only counts toward the bank if confirmed (or guessed); every past day counts automatically at midnight (derived on read; no write) unless it looks light; light/untracked days contribute 0. `mightBeMissingFood` (`utils.ts:225-228`) drives the "Missed something?" copy: light/untracked, or counted-but-under.
- `weekBank` (`utils.ts:250-272`): `banked = Σ delta (counted + estimated)`; `budget = Σ goals`; `remaining` = today (if in progress) + upcoming; `remainingTarget = Σ remaining goals`; `eatenToday` = today's logged kcal if in progress; `left = remainingTarget + banked − eatenToday`; `even = (remainingTarget + banked) / remaining.length`; `floor = remainingTarget × 0.8 / remaining.length`; `perDay = max(even, floor)`; `overAtFloor = (perDay − even) × remaining.length`.
- **Projected week / "plan"**: `restOfWeekPlan` (`tide:194-206`) is the version Week/Today use for the days after today (section 6.5).
- **Adherence**: the old adherence score is gone from the UI; the only remnant is "At or within target: N of M counted days" in the details sheet, via `classifyCalorieDay` (`App:5512-5527`): Cutting good if `intake <= target`, else over; Maintaining good within ±150 of target (under < −150, over > +150); Bulking good from target to +300 (under < target, over > target+300).
- **Tracking modes** (`TrackingMode`): bank maths is identical for all three. Mode changes wording: Today hero "left" → "to go" for Bulking (`App:2457`); headline words (6.5.1); pace lead (`paceLead` `App:5584-5588`); Log food after-this line "left|to go|over target" (`App:4799-4803`); the menu-pick prompt rule (`menuPick.ts:200-204`); details-sheet "at or within target" bands. `trackingMode` is stored in each day's snapshot, and the headline uses the mode of the first counted day (or Cutting if counted days mix modes, `App:2280-2282`).

### 6.5 How the Week screen's headline numbers are computed and displayed (exact rules)

Notation: `fmt(x) = Math.round(Number(x)).toLocaleString()` (`utils.ts:10`); `energyText(state, kcal)` = `${fmt(kcal × (kJ ? 4.184 : 1))} Cal|kJ` (`utils.ts:363-373`). All conversions happen at display; no rounding is done in storage or in `weekBank`.

**(1) The "+N Cal banked" headline.**
- Rendered by `bankHeadline` (`App:2279-2293`) in two places: Week's big number + label (`App:5698-5701`, `bankNumber = headline.value`, label = `headline.label` + chevron) and Today's "This week" row, right column, first line `{headline.value} {headline.label}` (`App:2662`).
- Value source: `week.banked` = Σ `delta` over `week.counted` = days whose `intake != null`, i.e. status **counted** or **estimated** (`utils.ts:220, 252, 254`). The decision of who is counted is `bankDay` (`utils.ts:206-222`, rules in 6.3).
- **Does it include today?** Only if today has been confirmed (Done for today / That's everything, with > 0 Cal logged) or has a rough guess. An ordinary today, partial or over, is **excluded**: it sits in `remaining` and only moves `left` and the plan. All earlier days of the week are included automatically unless light/untracked. So a day that is far over, still open, does not change "+N banked" until midnight (or until confirmed).
- `delta` uses `goalForDate` (the locked per-day snapshot, or current Settings for an unconfirmed future/current day), **not** the day's custom/spread target: a custom 2,400 target on a day finished at 2,300 banks as 1,800 − 2,300 = −500 although Today's hero showed "100 Cal left".
- Formatting (`App:2279-2293`): Cutting, `banked >= 0` → value `signedEnergyNumber(banked)` (e.g. "+320"; exactly 0 → "0"), label `Cal banked`; Cutting, `banked < 0` → value `fmt(|banked|)` (no sign, e.g. "410"), label `Cal over so far` while days remain, `Cal over` once the week is finished; Maintaining/Bulking (or mixed-mode → Cutting) → `|banked| < 1` → "0" / `Cal from target`; else value `fmt(|banked|)`, label `Cal under` or `Cal over`. In kJ mode the label is `kJ ...`. Before the week starts: number = largest day target, label `Cal a day` (`App:5677, 5700`).

**(2) "N Cal left this week" and the "about N" allowance.**
- **"N Cal left this week"** (Week platter, `App:5802-5808`): `week.left < 0 ? \`${energyText(-week.left)} over this week\` : \`${energyText(week.left)} left this week\``; finished weeks show `${energyText(week.budget)} budget`; sub-line `${counted.length} of 7 days counted · average ${energyText(avg)}`. Same number in the details sheet as "Left this week" / "Over this week" (`App:5845`). Formula `left = remainingTarget + banked − eatenToday` (`utils.ts:268`) with base goals. **It includes today**: today's whole base target is in the pool and only what is already logged today is subtracted; unspent allowance of today therefore counts as "left". If today is confirmed, today leaves the pool and its delta joins `banked`.
- **"about N" for the days after today** (Week sentence `App:5596-5611`; Today pace line `App:2296-2304`): `restOfWeekPlan(week.days, week.banked, today, todayTarget)` (`tide:194-206`) where `todayTarget = resolveDayCalorieTarget(state, today).effective` (`App:5603, 2299`):
  - exists only if today is in progress and at least one later day remains; otherwise `null`;
  - `even = (Σ base goals of later days + banked + today's base goal − max(eaten today, todayTarget)) / later days`; `floor = Σ later goals × 0.8 / later days`; `perDay = max(even, floor)`; `overAtFloor = (perDay − even) × later days`; `todayExtra = max(0, eaten − todayTarget)`.
  - i.e. today is assumed to use **at least** its target (unspent allowance is not handed to tomorrow), anything eaten above it comes off the later days, and no later day is asked to go under 80% of its base target. Later days' own custom targets and spread adjustments are ignored.
  - Display: `about ${aboutEnergyText(perDay)}` rounded to the nearest 10 Cal (50 kJ), see (4).
  - Worked contrast: banked 0, today goal 1,800 with 600 eaten, 3 later days at 1,800: platter says "6,600 Cal left this week" (= 7,200 − 600) while the sentence says later days "can each be about 1,800 Cal".
  - Last day of the week (`remaining` = [today] only): uses `week.left` instead (sentence 1 in the list below). When `plan` is null for other reasons (e.g. today already counted), `bankAnswer` uses `week.perDay` (`utils.ts:257-259`) which does not subtract anything eaten today.
- Today's "This week" row second line (`weekPaceLine` `App:2296-2304`): `${planDaysLabel(plan.days)} about ${about(plan.perDay)}${plan.days.length > 1 ? ' each' : ''}` e.g. "Sat & Sun about 1,800 each" / "Sun about 1,800"; `Week finished`; `About ${about(week.left)} left this week` / `About ${about(-week.left)} over this week` (only today left); fallback `${planDaysLabel(week.remaining)} about ${about(week.perDay)}${' each'}` (e.g. "Mon–Sun about 1,800 each" for a week that hasn't started). `planDaysLabel` is `Sat`, `Sat & Sun` or `Fri–Sun` (`App:2272-2276`). It omits the "will still finish over" caveat.

**(3) The status copy and the rule that picks it.** `weekAnswer` (`App:5596-5611`) → `.tl-answer` (`App:5702`), wrapped by (`App:5655-5657`). First match wins:
  0. `!started` (Monday is after today): `This week hasn’t started yet. Its budget is ${energyText(week.budget)}.`
  0b. started, finished, nothing counted or held: `Nothing was logged this week.`
  1. only today remains: `week.left >= 0` → `Last day of the week: about ${aboutEnergyText(week.left)} left after what’s logged.`; else `Last day of the week. It will finish about ${aboutEnergyText(-week.left)} over, and the bank resets Monday.`
  2. `plan == null` → `bankAnswer` (`App:5547-5563`): nothing remaining → `Finished ${energyText(banked)} under target.` / `Finished ${energyText(-banked)} over target.` / `Finished right on target.`; floor binding → `Aim for about ${amount} ${when}. The week will still finish about ${aboutEnergyText(overAtFloor)} over, and the bank resets Monday.` (`when` = `today` | `on <Weekday>` | `a day`); one day left → `Today can be about ${amount} in total.` | `<Weekday> can be about ${amount}.`; else `The ${n} days left[, including today,] can average about ${amount} each.` (the "including today" variants look unreachable, inferred).
  3. `plan.overAtFloor > 0 && showsRounded(overAtFloor)` (floor is binding): `Aim for about ${amount} a day. The week will still finish about ${aboutEnergyText(plan.overAtFloor)} over, and the bank resets Monday.`
  4. `plan.todayExtra > 0 && showsRounded(todayExtra)`: **`Still on track. Today’s extra ${energyText(todayExtra)} comes off ${plan.days.length > 1 ? 'the days after' : who}: about ${amount}${each}.`**
  5. otherwise: `${paceLead(mode, banked)} ${who} can${each} be about ${amount}.`, e.g. "Right on pace. Saturday and Sunday can each be about 1,800 Cal."
  - **Rule for "Still on track."**: a rest-of-week plan exists (today in progress with later days), the 80% floor is *not* binding, and today's logged calories exceed today's effective target by >= 5 Cal (>= 25 kJ). It does not look at the size of the overage, the sign of the bank, or the tracking mode: it appears after a 100 Cal or a 1,500 Cal overrun alike, so long as the later days' average stays >= 80% of target. Today's own screen has no equivalent text.
  - `paceLead` (`App:5584-5588`, thresholds on raw kcal, ±100): Cutting: banked >= 100 → "A little ahead."; <= −100 → "Easy to even out."; else "Right on pace." Maintaining: |banked| >= 100 → "Easy to even out."; else "Right on pace." Bulking: banked >= 100 → "A little behind."; <= −100 → "A little ahead."; else "Right on pace."
  - `who` (`planDaysPhrase` `App:5577-5581`): "Sunday", "Saturday and Sunday", or "The 4 days after today".
  - Other status strings that appear with these numbers: story "`Tuesday` took the week to −320. `Thursday` brought it back." (`App:5659`; only when the running balance fell to <= −100 and later returned to >= 0); tide label "on pace" (static text, `App:5722`); per-day status words `BANK_STATUS_TEXT` (`App:5565-5572`): '' (counted), "rough guess", "looks light, check it", "nothing logged, counts as on target", "today, still in progress", "coming up"; platter titles "`Thursday` looks light" / "`N` days look light"; Today hero status strings (2.1); day status card strings (2.1); week row notes "`Tue` to check", "`N` days to check", "`k` of 7 counted".

**(4) Every place rounding happens.**
  - No rounding in `entryTotals`/`sum`/`bankDay`/`weekBank`/`restOfWeekPlan`; each displayed number is rounded independently at render by `fmt`, so displayed parts need not add to displayed totals. Rounding is `Math.round` (half rounds **toward +∞**: `Math.round(567.5) = 568`, `Math.round(-567.5) = -567`).
  - Signed vs absolute rounding: Week's deltas row, details table and bank headline apply `fmt` to the **signed** value (`signedEnergyValue` `App:5533-5536`) while "N over/under" strings apply it to the **absolute** value (hero `App:2456`, `bankHeadline` `App:2285`, `energyText(-delta)` `App:2952`). For an underlying −567.5 the row shows "−567" but Today's hero/status card say "568 Cal over". The sum of the seven displayed deltas can also differ from the headline, which is rounded once from the unrounded sum (`App:5730` vs `App:2287`); the details table's Balance column is a running sum of unrounded deltas rounded per row (`App:5828-5838`).
  - "about N": `aboutEnergyText` (`App:5539-5542`) = `fmt(Math.round(displayValue / step) × step)`, step 10 Cal or 50 kJ, applied after kJ conversion. Used for: the allowance `perDay`, `overAtFloor`, and the last-day `week.left` in the Week sentence and Today pace line. **Not** used for: the bank headline, the platter "N Cal left/over this week", `todayExtra` in the "Still on track" line, the "Finished N Cal under/over" sentence, "Its budget is", the day status card, tile aria-labels, averages. So one sentence can mix to-the-Cal and to-the-10 figures, and the Week screen can show both "about 1,290 Cal left after what’s logged" (sentence) and "1,288 Cal left this week" (platter) for the same `week.left`.
  - `showsRounded` (`App:5591-5593`): `Math.round(displayValue/step) >= 1`, i.e. >= 5 Cal (25 kJ); only gates whether an over-clause is shown.
  - Spread-bank target on Today is unrounded (`utils.ts:274-282`): "Target 1,948 · with bank" while Week says "about 1,950 each". It also doesn't react to today's intake whereas Week's `perDay` does.
  - Hero: `fmt(|goal − eaten|)` and the feet line `fmt(eaten)` are rounded independently, so with a 1,800 target and 1,232.5 eaten they read "568 left" and "1,233 eaten".
  - Log food "After this" line: `Math.round(target − eaten − total)` to whole kcal first, then `energyTextForUnit` converts and rounds again (`App:4798-4803`) (double rounding for kJ users).
  - Sources of fractional kcal feeding all this: serving multipliers (0.5, 1.5, 100 g/100), kJ typed values converted `÷4.184` unrounded (`utils.ts:385-388`) and kJ goals saved unrounded (`App:1816`), kJ display `×4.184` (`utils.ts:363-365`), Gemini base values rounded to whole Cal in the sheet before saving (5.4), batch serves rounded per logged serve (`App:1540-1543`).
  - Explicit integer rounding in data: rough guesses `Math.round` (`utils.ts:141`, `state.ts:127`), day overrides (`utils.ts:309, 328`), Gemini parse (calories whole, macros 0.1 g, `aiEstimate.ts:167-177`), menu parse (whole numbers, `menuPick.ts:257-266`), batch parse (`mealPrep.ts:119-131`).
  - Negative zero: `fmt(-0.3)` = "-0", so `signedEnergyNumber` can print "−0"; a tiny positive prints "+0".
  - Tide chart geometry uses `toFixed(1)` only for SVG coordinates (`App:5667, 5718`).

**(5) Sign and wording conventions; which limit the bars show.**
  - Per-day deltas row on Week (`App:5726-5744`, no unit, aria-hidden): counted → `signedEnergyNumber(delta)`: **"+304"** (under target, banked) / **"−38"** (over target), using a true minus U+2212 (`App:2265-2267`); estimated → `≈` + signed (e.g. "≈−500"); light → "Check"; untracked → "—"; today → `${amount} left` / `${amount} to go` (Bulking) / `${amount} over` where amount = `fmt(|effective target − eaten|)` and a line break when the amount is 5+ characters (`App:5734-5740`); upcoming → empty. Only today's cell gets a colour class (`today` accent, `over` amber); finished negatives are not coloured. Positive always means "under target", so for Bulking a "+" means behind, with no change of sign.
  - Same sign convention in the details table "vs target" and "Balance" columns (`App:5832-5838`; "held", "today", "—" for non-counting rows). Absolute wording elsewhere: "`730 Cal over`" / "`304 Cal under target`" (status card `App:2950-2952`: `${energyText(delta)} under target` / `${energyText(-delta)} over target` / `Right on target`, note delta = 0.3 prints "0 Cal under target"), Today hero "`Cal over today`", tile aria "`1,288 Cal, 512 Cal under target`". There is one more minus glyph: `signedEnergyText` (ASCII "-", used only in the rough-guess title fallback `App:3044`).
  - **Which limit the bars use**: Week's tiles and the small number at their top-right (`.tl-tiles-target`, `App:5777`) show `fmt(maxGoal)` = the largest per-day target in the week, where **today's** target is the *effective* one (custom or spread-adjusted, `App:5672`) and **every other day, including tomorrow, is its base goal** (the locked snapshot for finished days, current Settings for upcoming days; custom overrides and spread are ignored for them). Each tile's room height and target line use that same per-day goal (`App:5749-5750, 5769-5770`); bar scale is `maxGoal × 4/3 = 200px` (`App:5673-5675`). The planned allowance (`perDay`, "about N") is never drawn on the tiles. Today's own "Target" label shows the adjusted limit with a suffix "· custom" or "· with bank" for any selected day (`App:2479, 2611`).

### 7.6 The arc / sun on Today: how it is drawn and what it encodes
- Geometry (`tide:57-116`): hero canvas viewBox `0 150 390 198`, container `aspect-ratio: 390/198`, preserved `xMidYMax meet` (`App:2589`, `css:1800`). Semicircle centre (195, 348), radius 158, feet at (37, 348) and (353, 348), apex y = 190. A 1px horizon line is drawn at the bottom of the hero (`css:1801`).
- Angle = `π × (1 − min(calories, target) / target)`: empty day = sun on the **left** foot; eaten = target → sun on the **right** foot. So left-to-right is "how much of the target has been used", not clock time.
- **One lit segment per entry**, in eaten order (morning → afternoon → evening, then logged order), 4px stroke in `--arc`, round caps, with a 4px gap between segments (`sunArc` `tide:88-116`). The dotted remainder (2.5px, `stroke-dasharray: 0 8`, round caps, `--arc-rest`) runs from the sun to the right foot and disappears at/after target.

## 8. Motion and interaction

Timing tokens: `--motion-fast 140ms`, `--motion-medium 210ms`, single house easing `--ease-ios: cubic-bezier(.2, .8, .2, 1)` (`css:81-83`), also `SEARCH_EASE` (same curve, `App:3432`). Nothing uses spring physics; "springing back" is a 220ms ease-out curve. Nothing is rubber-banded except the week strip (1/4 resistance). There are no haptics (no `navigator.vibrate`), no sound.

### 8.1 CSS
- Every `button`: transitions `transform, opacity, background-color, border-color, color, box-shadow` 140ms; `button:active { transform: scale(.972); opacity: .92 }` (`css:152-153`). Rows and pills override with their own press states (e.g. `scale(.985)`, background tint, or no transform on tab bar / list rows).
- Screen settle: `.view-transition { animation: pageSettle 210ms ease-ios }` = opacity .82 → 1 only (`css:158-161, 210-212`); replayed by `useSettleAnimation` (`App:442-452`) when `selectedDate`, `bankingWeekStart`, journal month/day change (class removed, reflow, re-added) instead of remounting. Images fade in with the same keyframes (`css:1295-1303`).
- Sheets: see 8.3. Backdrop fade `modalBackdropIn` 210ms; non-sheet panel `modalPanelIn` 210ms (translate 14px + scale .985 + fade) in, 140ms out.
- Toast in: `toastIn` 210ms; no out animation.
- Tab bar hide/show: `transform .2s ease-ios, opacity .2s` (`css:1971`).
- Week strip selected lens: opacity 140ms; status scrim opacity 140ms; fav heart `favPop` 320ms scale 1.28 (`css:1445-1446`); meal-prep pips 200ms fill; details chevrons `.18s`; day-part segmented control `entry-part-in` 160ms; calendar/slider have no motion; spinner `menuPickSpin .9s linear infinite` (`css:1082-1083`); swipe-confirm fill/handle `.16s ease`.
- Hover: `border-color` tint on cards for `(hover: hover) and (pointer: fine)` only.

### 8.2 JS-driven (Web Animations API or inline styles)
- **Week strip swipe** (`useWeekSwipe` `App:2324-2409`): pointer events with capture after 10px horizontal travel; the strip follows the finger (`translateX`, opacity down to .5); commit when |dx| > min(80px, 20% width) or (speed > 0.45px/ms and > 24px); commit = out 130ms `ease-in` → synchronous state change via `flushSync` → in 240ms ease-ios from ±50% width with opacity; cancel = 220ms ease-ios settle. Past the current week the drag is divided by 4 and no fade. Not interruptible mid-animation (a new pointerdown after commit starts fresh; the out animation uses `fill: forwards` then is cancelled).
- **Search overlay** (`FoodSearch` `App:3470-3787`): WAAPI. Opening: the bar animates from the Today field's rectangle to its place (320ms, `SEARCH_EASE`), Cancel slides in from the edge, backdrop fades 240ms, results fade+rise 260ms with a 140ms delay. Closing via Cancel: reverse (300ms bar, results fade 90ms, backdrop 220ms with 80ms delay). **Interruptible**: if Cancel is hit mid-open, the in-flight transform/opacity values are read with `getComputedStyle` and the close starts from there (`midway`, `App:3495, 3566-3573, 3588`). Picking a food just fades the overlay out (180ms) while the sheet comes up. Reduced motion → 160/180ms opacity fades only.
- **Sheet drag-to-dismiss** (`Modal` `App:574-668`): direct manipulation. After 8px of vertical travel the panel's `transform` follows the finger 1:1 (transition disabled) and the scrim fades toward 25%. Release: fast flick or far drag → out `min(CLOSE_MS, 220)ms` ease-ios then unmount; otherwise back in 220ms. No velocity carry-over, no spring, not interruptible once closing starts.
- **Sheet open/close**: bottom sheets use a CSS transition on `transform` (320ms ease-ios) toggled by the `entered` class set one animation frame after mount; closing removes the class and waits 320ms (JS `setTimeout`) before unmounting. Non-sheets: 180ms.
- **Swipe-to-confirm** (`SwipeConfirm` `App:3108-3167`): progress = pointer x / track width; confirm at 0.82 (sets progress to 1, 120ms later fires `onConfirm`); otherwise reset to 0 with the 0.16s transition. No haptic, no velocity logic, no label animation.
- **Long-press** (`DayLineRow` `App:2858-2886`): `pointerdown` starts a 450ms timer; `pointermove` > 10px cancels; `pointerleave/up/cancel` cancel; when it fires the menu opens at the press point (below it if it fits above the tab bar, else above; 196px x 200px estimate); menu items are inert (`pointerEvents:none`) until the finger lifts so release never selects; the following synthetic click is swallowed (`press.current.fired`). Right-click (`contextmenu`) and keyboard (Shift+F10, ContextMenu key) open the same menu. There is no press-down visual feedback (no scale/haptic before the menu appears) beyond the row's `:active` tint.
- **Measure-then-animate**: the keyboard stand-in input (`App:351-390`) and the manual-sheet focus hand-over poll `getComputedStyle(...).transform` each frame until the slide-in is finished (up to 800ms) before focusing (`App:4745-4758`).
- Count-up/transitions on numbers: none. The hero number, arc, tiles and tide line change instantly.

### 8.3 Reduced motion and transparency
- `@media (prefers-reduced-motion: reduce)` sets every element's `animation-duration` and `transition-duration` to 1ms and iteration count 1 (`css:1429-1438`), which also neutralises inline `transition` strings set by the drag-dismiss code (important beats inline) and stops the spinner. WAAPI code checks `matchMedia('(prefers-reduced-motion: reduce)')` itself in `useWeekSwipe` (`App:2330`) and `FoodSearch` (`App:3433, 3545, 3586`). Sheets still change state instantly rather than "crossfade".
- `prefers-reduced-transparency` handled for glass (`css:1982-1985`).

### 8.4 Scroll behaviour
Document scroll with per-tab restore (1.6); smooth scroll on re-tap and on `scrollIntoView` to Settings sections; instant scroll on week change; `overscroll-behavior: none` on html/body and `contain` in sheets/search results; search results get a 10px top fade mask (`css:2071`); chip rows and the Now chips scroll horizontally with hidden scrollbars (`css:1888-1889`); `.screen-swipe-zone` min-height keeps short screens tall; journal summary bar is sticky above the tab bar.

## 9. Accessibility, read from code

### 9.1 What exists
- **Landmarks/roles**: `<main class="app">`; `<nav aria-label="Main tabs">` with `aria-current="page"` (`App:914-921`); sparkle button `aria-label="Log with AI"`; Today's day strip is a `<nav>` with a long aria-label ("Days this week. Swipe sideways for another week."), each day button labelled with date + status and `aria-current="date"` when selected (`App:2555-2574`); hero `<section aria-label="N Cal left today. X eaten of Y.">`; Day line `<section aria-label="Day line">` with `<h2>` part headings; Week big number, tiles and tide chart carry full-sentence aria-labels (`App:5698, 5706, 5767`), decorative deltas/day labels/target label are `aria-hidden`.
- **Dialogs**: every `Modal` is `role="dialog" aria-modal="true" aria-label={title}` with a labelled Close button; search overlay likewise. `Escape` closes the topmost sheet, the long-press menu and the search overlay.
- **Menus/lists**: long-press menu is `role="menu"`/`menuitem`, first item focused on open, ArrowUp/Down cycle, Escape returns focus to the row, Shift+F10/ContextMenu key opens it (`App:2811-2836, 2876-2882`). Foods sub-tabs are `role="tablist"/"tab"` with `aria-selected`; chips/toggles use `aria-pressed`; hearts use `aria-pressed` and a named label.
- **Live regions**: toast `role="status"`; Logged-total chip row `aria-live="polite"` (`App:4873`); search result summary (`sr-only` polite, `App:3779`); menu-pick loading `role="status" aria-live="polite"` (`App:4537`); serves stepper output polite (`App:3918`). `sr-only` helper exists (`css:1441`) and is used to prefix search rows with "Favourite:" / "Recent:" and "Meal prep, logs a serve:".
- **Inputs**: most fields are wrapped in `<label>` via `Field` (`App:733-735`); calories and refine inputs have `aria-label`; textareas have labels; range slider has `aria-valuemin/max/now`.
- **Keyboard**: `SwipeConfirm` is a focusable `role="button"` that activates on Enter/Space (`App:3141-3150`); all other controls are real `<button>`s; native date picker for Today.
- **State not by colour alone**: hearts filled vs outline; over-target uses an amber dot + the word "over"; day status has text ("looks light, check it"); rough guesses get "≈" and a text label; held days get the word "Check".
- **System preferences**: `prefers-reduced-motion` and `prefers-reduced-transparency` handled (8.3); light/dark follows the setting or `prefers-color-scheme`.

### 9.2 Gaps / risks visible in code
- **Modal focus**: no focus trap, no initial focus (except manual Log food), no focus restoration on close (except search overlay and long-press menu); background content is neither `inert` nor `aria-hidden`.
- **Zoom disabled**: `maximum-scale=1, user-scalable=no` in the viewport meta (`index.html:5`); text is px-based everywhere (no `rem`), so OS text-size settings in iOS standalone do not scale it.
- **Tiny text**: 10px (tab labels `css:1975`, nutrition-grid labels `css:801`, compact picker chips `css:879`), 11px (day-of-week header, tide label, tile target number, fav hints), 12px (feet line, delta row, many chips) in a UI aimed at glanceable use.
- **Unnamed or weakly named controls**: the day-target range slider has no label (`App:808-824`; the visible label belongs to the number input); Foods search and the in-sheet search rely on placeholders ("Search your usual foods", "Search saved foods"); the Journal List/Collage control is a `role=group` of two buttons that both toggle and neither exposes `aria-pressed` (`App:5273-5276`); tablist has no `tabpanel` association or arrow-key navigation; the calendar button is a `<label>` wrapping a transparent date input (labelled by `aria-label` on the label).
- **Gesture-only paths**: Log food's primary save is a slide-to-confirm (keyboard users can press Enter/Space on it; it has no `onClick`, so an assistive-technology activation that only fires a click is probably not handled (inferred), and no single-tap alternative exists for touch users); "Log again today", photo and delete exist only in the long-press menu or the edit sheet.
- **Errors**: inline error paragraphs (`.ai-quick-log-error`) have no `role="alert"`/`aria-live`, so a screen reader is not told when an estimate fails. The hero's `aria-label` is static text on a section, not a live region, so changes after logging aren't announced (the toast is the only announcement).
- **Unstyled native dialogs** (`confirm`, `alert`) for destructive actions and import errors (3.21).
- **Default tab order**: the floating tab bar and sparkle button come after `<main>` in DOM order, so keyboard users reach them last; the hidden-on-focus behaviour (`aria-hidden` on the tab bar while a text field is focused outside a modal) removes navigation while typing in Foods/Settings fields.
- `user-select: none` on `body` except inputs/pre/`.selectable` (`css:128-149`), so notes, names and AI explanations cannot be selected or copied (the Gemini error details are opted back in).

## 10. PWA, offline, update, backup

- **Hosting/base path**: GitHub Pages at `/Simple-Calories-Ledger/` (`vite.config.ts`); CI (`.github/workflows/deploy.yml`) on push to `main`: `npm ci` → `npm test` → `npm run build` → upload `dist` → deploy Pages.
- **Install**: `public/manifest.webmanifest` (name/short_name "Dawni", `display: standalone`, `start_url`/`scope: ./`, `theme_color`/`background_color #0A1B1E` (dark) although the default theme is light; the runtime meta `theme-color` switches to `#EEF4F3` for light), icons 192/512 PNG declared `any maskable` (the same files for both purposes), `apple-touch-icon`. `apple-mobile-web-app-capable`, title "Dawni", black-translucent status bar (`index.html:8-12`). A duplicate identical `manifest.webmanifest` sits at the repo root (unused).
- **Service worker** (`public/sw.js`, 91 lines; registered from `pwa.ts:64-86` as `./sw.js`): cache `dawni-<APP_VERSION>`; precache `./`, `./index.html`, manifest, 3 icons; **no `skipWaiting` on install** (the new worker waits until the app posts `SKIP_WAITING`); `activate` deletes older `dawni-*` caches and claims clients. Fetch strategies (same-origin only): `version.json` → network only, `no-store`; `/commonfooddb/` → network-first with cache fallback; navigations → network, caching a fresh `index.html`, falling back to cached `./`/`index.html`; everything else (hashed JS/CSS/fonts/images) → cache-first with runtime caching. Offline therefore works after the first online load. The food database is also cached in IndexedDB. Gemini calls obviously need network and have no offline messaging.
- **Update checker** (`pwa.ts`, `App:1033-1046`): on load, registers the SW, clears reload markers, runs `checkForAppUpdate` (fetch `./version.json` with `no-store`, compare 4-part versions; if a worker is already waiting it uses that), and `watchForUpdatesOnResume` re-checks on `visibilitychange`/`pageshow` at most every 20 minutes (with `reg.update()`) and skips versions the user dismissed. Any found update opens the **"Update available"** sheet (3.7). "Update now" → if a worker is waiting: `SKIP_WAITING`, reload on `controllerchange` (hard fallback reload after 2.5s); else `registration.update()` then navigate with `?appVersion=…&reload=…` cache-busting params (stripped again on next launch). Settings → "Check for updates" forces a check and toasts "Update ready" / "You are on the latest version" / "Could not check for updates".
- **Notes shown**: the sheet lists `availableUpdate.notes.slice(0, 5)` (`App:1662`). `release-notes.json` is a cumulative list of 19 items ordered oldest-first (Tidelight first, fonts last), so the first five shown are the *oldest* notes, not the newest (inferred from file order). A "Not now" is remembered only for resume-time checks; the launch-time check (`App:1041-1042`) does not consult the dismissal, so the sheet returns on every cold start while an update is pending (inferred).
- **Versioning**: edit the 4-part `version` in `package.json` by hand + `src/release-notes.json`; `scripts/prebuild.mjs` (run by `predev`/`prebuild`) writes the version into `public/sw.js`, `public/version.json` and `index.html`'s `app-version` meta; a bump is what makes the SW bytes change (`version.ts:1-5`).
- **Backup reminder** (`App:1048-1059`, `backup.ts:280-290`): once per calendar day, when nothing else is open, there is data (entries or foods) and `backupAgeDays >= reminder days (3/7/14, default 7)` → sheet (3.8). Age counts from `lastBackupAt`, else from the oldest entry. Reminder interval is changed in Settings → Backup.
- **Export** (`backup.ts:296-322`): JSON `{exportedAt, app:'calorie-tracker', version, counts, state}` including everything (settings, Gemini key, photos as base64 data URLs, custom databases, batches). Uses the Web Share sheet with a `File` when available, else a download named `calorie-tracker-backup-YYYY-MM-DD.json`. Success sets `lastBackupAt` and toasts "Backup exported" (cancel is silent, failure "Could not export backup"). No automatic or scheduled backup, no cloud, no restore preview.
- **Import** (`App:1882-1892`, `backup.ts:324-329`): choose a JSON file; invalid → `alert('Invalid backup file')` (or the JSON error); valid → native `confirm("Import backup and replace current local data? This backup has N entries and M photos.")`; replaces all local data (no merge) and toasts "Backup imported: N entries". Custom food database import is separate (JSON with `id,name,version,items[]`, replace-by-name confirm).
- **Clear local data**: native confirm "Delete all entries, foods, settings, and photos from this browser? Export a backup first if unsure." then resets state to defaults (does not clear the separate IndexedDB keys for the Gemini key profile, food database cache, or last menu pick).
- **Privacy statements in UI**: "Dawni keeps your data on this device"; Gemini key "stays on this device and is included in backups"; menu photos "aren't saved to your journal".

### 11.3 Today and Week are intertwined
- Today computes the whole week bank (`weekBank(state, weekStart)` each render) for the strip, the "This week" row and the pace line (`App:2483-2519`), and `RichStatsView` re-derives the same plus an effective target for today (`App:5672`).
- Shared helpers live in whichever section defined them first: `BANK_STATUS_TEXT` (defined in the Week section `App:5565`, used by Today's strip `App:2572`); `signedEnergyNumber` (Today block `App:2265`) vs `signedEnergyText/Value` (Week block `App:5529-5536`); `planDaysLabel` (Today, `Sat & Sun`) vs `planDaysPhrase` (Week, `Saturday and Sunday`); `WEEKDAY_SHORT` vs `WEEKDAY_LONG`; `aboutEnergyText` (Week block) used by Today's `weekPaceLine`; `bankHeadline` (Today block) used by Week's answer and number.
- The sentence logic (`weekAnswer`, `bankAnswer`, `paceLead`) is in `App.tsx`, untested, and partly duplicates numbers computed in `weekBank` and `restOfWeekPlan` (`perDay` exists in both and differs: 6.5).
- The sky (`useSky`, `skyStyle`) is shared by both screens; it writes `--status-scrim` and `data-sky-at-rest` on `<html>` as side effects.
- Rebuilding Today and Week means touching ~1,500 lines of component code plus the Tidelight CSS block, and deciding which of the four target concepts each number should use.

### 11.5 Easy vs hard to rebuild
- **Easier**: all money-maths and AI parsing is pure and tested (`utils`, `tidelight`, `aiEstimate`, `mealPrep`, `favourites`); the visual layer for Today/Week is almost entirely in two components plus the last ~700 lines of CSS (`.tl-*`); design tokens exist for colour, radius, tap size, motion; fonts are bundled; theme and accent are runtime variables; the data model is stable and normalised on load; the sky/arc geometry is isolated in `tidelight.ts`.
- **Harder**: no component files, so any restructure starts by splitting `App.tsx`; CSS has three generations stacked with dead code, so selectors cannot be reasoned about locally; screen text is generated inline (week sentences, headline labels) rather than from a copy table; Log food is one 330-line component with three modes and many prefill sources (`openMode` / `reviewing` branches); the Modal engine mixes presentation, scroll lock, gestures and iOS workarounds; no router means no deep links (each redesigned flow must keep its entry points in `App` state); Today re-renders everything every minute.
- **Other**: no ESLint/Prettier configured (devDependencies are types only); TypeScript `strict` is on; strings are inline English (AU spelling) with mixed locale use (`en-AU` weekday names vs the system locale for numbers/dates); `README.md` still describes the old PWA setup.

## 12. Friction noticed (observations only)

1. Terminology drift: "Log food" / "Log Food" / "Log with AI" / "Log manually" / "Estimate with Gemini" / "Pick from a menu" vs "Help me pick from a menu"; "Foods" tab vs "My Foods"; "Week bank" / "banked" / "bank" / "Calories Bank" (PDD); "Cal" vs the PDD's "calories"; "Recent" vs "Recent foods".
2. The sparkle ("Log with AI") is the only global add control and opens a sheet whose first, second and third rows are all AI; manual logging is only on Today. The PDD's "core manual tracking is free and primary" is inverted in placement. From non-Today tabs the sparkle silently switches to Today and resets its date.
3. Saving a logged food needs a slide-to-confirm; there is no tap-to-save in prefill/edit modes. Enter in a field likely doesn't submit.
4. The "Estimating…" toast promises "You can close this" while the sheet is locked; there is no timeout or cancel for Estimate/Batch, and no model/tier info during the wait.
5. The Now line chips are described in the release notes as "one tap from logging" but open the full Log food sheet; only meal-prep rows are one-tap logs.
6. Today's "Add a rough meal" / "Rough guess for the day" actions are hidden before 17:00 while under 90% of target.
7. Week numbers on one screen use different bases (base goal vs effective target vs plan) and different rounding (to the Cal vs to 10): "1,288 Cal left this week" under "about 1,290 Cal left after what’s logged"; custom day targets don't change the banked result; a custom target on a future day is ignored by the week plan and tiles (6.5).
8. "Still on track." is triggered purely by being over today's target while the floor isn't binding; it appears after any size of overrun.
9. Settings is reachable from one place on one tab; "Done" always returns to Today (and resets the date). The app can cold-start on Settings.
10. Update sheet shows the first five (oldest) of a cumulative notes list and re-prompts after "Not now" on each launch.
11. Foods and Settings goals decimals: `Number()` on every keystroke likely prevents typing "1.5" (FoodModal, Goals).
12. Destructive actions use native `confirm`/`alert`; Remove photo and Log again have no confirmation/Undo; Delete entry is confirm-only, no Undo toast (other actions do offer Undo).
13. The AI trust copy is inconsistent: the menu sheet explains what is sent (but omits the saved "About you" text); the estimate sheet does not. Disclaimers differ in tone ("AI estimates can be wrong" vs "Dawni treats AI output as editable, not guaranteed").
14. Accessibility: no focus trap/return in sheets, pinch-zoom disabled, 10-12px micro text, unlabeled range slider, several 36-40px targets, amber `--color-review` at 4.2:1 on white.
15. Visual debt: ~110 dead class selectors, three CSS generations, five food-row styles, three date navigators, `data-swipe-lock` leftovers.
16. Brand drift: Dawni (UI), Simple Calories Ledger (repo, share file names, backup title), Calorie Tracker (backup file prefix, localStorage keys), "weekly food journal" (page title), "Weekly Calorie Tracker" (Settings).

## Appendix C. Fifteen most important facts
1. Five tabs in code, four in the floating glass tab bar: Today, Week, Journal, Foods. Settings is only reachable from a sliders icon on Today and "Done" always returns to Today (`App:96-108, 2550, 6004`).
2. There is no global "+" button. The only global add control is the sparkle ("Log with AI") beside the tab bar; it jumps to Today and opens a sheet whose three rows are all AI (`App:1129-1132, 2045-2073`). Manual logging is a "Log manually" row and a "Search foods" button on Today.
3. All sheets share one `Modal` engine (bottom-anchored at <=480px, centred above), dismissed by X, scrim tap, swipe down or Esc; no focus trap or restoration (`App:529-731`).
4. Saving a log entry requires a slide-to-confirm gesture; there is no tap-to-save in prefill/edit modes (`App:3108-3167, 4960`).
5. Fastest logging paths: meal-prep serve 1 tap; repeat via long-press 2; manual 2 (+typing); saved food via Search 3; Gemini text 5 (+typing +wait); menu pick 6; "copy day" does not exist (section 4).
6. Data is local-only in IndexedDB (whole state rewritten on every change); Gemini is called straight from the browser with the user's key, no backend, no request timeout (`App:980-985`, `geminiEstimate.ts`).
7. Gemini returns `total`/`servingsEaten`/`gramsEaten`/`per100g`; the app stores per-unit `base*` values and a `portion`, and derives totals; AI results are labelled Estimated / From label / From menu / Rough guess, with confidence and assumptions flattened into notes (`aiEstimate.ts:214-270`).
8. Week bank: Mon-Sun; a past day counts at midnight unless logged < 60% of target (held as "light"); today counts only when confirmed; headline "+N Cal banked" = sum of counted-day deltas from base goals; "N Cal left this week" includes today; "about N" assumes today uses at least its target and floors days at 80% (`utils.ts:206-272`, `tidelight.ts:194-206`).
9. Week numbers mix bases and roundings (Cal vs nearest 10; signed vs absolute rounding; base vs effective target), so the same value can read 1,288 and 1,290, or -567 and 568 (6.5).
10. Visual system: clock-following sky gradient (dawn/day/dusk/night x light/dark), a sun-on-arc hero where sun position = share of target eaten, Fraunces Soft for titles/big numbers, Nunito for text, teal accent, outline-free white/teal cards, glass chrome (`tidelight.ts`, `styles.css`).
11. Over-target is amber, never red; copy follows "no guilt" rules, but some strings are inconsistent (sections 4g, 12).
12. Motion: one easing curve (.2,.8,.2,1), 140/210/320ms, no springs, no haptics, no animation of the sun/numbers; reduced-motion handled globally and in the two WAAPI places.
13. `App.tsx` is 6,069 lines, `App()` alone is 1,266; `styles.css` stacks three design generations with ~110 dead selectors; pure logic modules are separate and tested (88 passing tests), UI has no tests.
14. Accessibility gaps: pinch-zoom disabled, 10-12px micro text, several 36-40px targets, unlabeled range slider, no focus management in sheets, amber text at 4.2:1 on white in light mode.
15. PWA: network-first/cache-first service worker, manual-version update checker with a sheet that lists the oldest 5 notes, weekly-ish backup reminder, JSON export/import that includes photos and the API key.
